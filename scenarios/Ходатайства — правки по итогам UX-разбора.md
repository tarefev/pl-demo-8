# Конструктор ходатайств: правки по итогам UX-разбора

Разбор спроектированных визардов с позиции адвоката — отдельно взгляд человека,
который открывает инструмент впервые, и взгляд того, кто работает с ним ежедневно.
Документ дополняет проект и приложения; на момент составления в площадке 8 реализован
только слой данных (`js/motions.js`).

Статус: к реализации, порядок — по § 4.

---

## 1. Первое использование

### 1.1. Каталог: недопустимость и исключение — один пункт, а не два

**Что не так.** В каталоге рядом стоят «О признании доказательства недопустимым» и
«Об исключении доказательства (в суде)». Для адвоката это одно действие на разных
стадиях. Выбирать между ними — значит думать о процессуальной технике вместо задачи,
и ошибиться на первом же экране.

**Как надо.** Один пункт: «О признании доказательства недопустимым». Стадия известна
системе, она и определяет наименование, адресата, нормы и просительную часть: на
следствии — признание недопустимым (ст. 75, 88), в суде — исключение (ст. 235).

**Затрагивает:** каталог `MOTION_CATALOG`, определения `inadmissible` и `exclude` —
объединяются в одно с развилкой по стадии.

### 1.2. Названия стадий — на языке адвоката

**Что не так.** «Окончание следствия» понятно только тому, кто помнит про ст. 217.

**Как надо.**

| Было | Стало |
|---|---|
| Предварительное следствие | Следствие идёт |
| Окончание следствия | Следствие окончено, знакомлюсь с делом |
| Судебное разбирательство | Дело в суде |

Пояснение про статью остаётся подсказкой второй строкой, а не названием.

**Затрагивает:** `MOTION_STAGES`.

### 1.3. Пресет в длинных списках

**Что не так.** Тридцать пунктов материалов дела даже в двух группах — стена. Первая
реакция новичка: ставить галочки подряд.

**Как надо.** Над списком — кнопка, закрывающая типовой случай: «Всё, к чему есть
доступ на этой стадии». Она отмечает доступные пункты одним нажатием; точечный выбор
остаётся для тех, кому нужно именно оно. Аналогично в других длинных перечнях:
у каждой группы — «выбрать всю группу».

**Затрагивает:** движок шага `multi-group`.

### 1.4. Недоступные пункты объясняются словами

**Что не так.** Пункт, недоступный до окончания следствия, выглядит просто серым —
как будто интерфейс сломался.

**Как надо.** Прямо в строке — короткая приписка «доступ по окончании следствия».
Предупреждение при выборе остаётся, но пользователь понимает причину сразу.

**Затрагивает:** рендер списка материалов, `MATERIALS_EARLY_ACCESS`.

### 1.5. Обоснование не бывает пустым

**Что не так.** Пустое поле с подписью «изложите обстоятельства» — момент, когда
адвокат закрывает инструмент и уходит в Word к своим заготовкам.

**Как надо.** В поле уже стоит каркас, собранный из выбранных пунктов и фактуры дела:
кто, по какому делу, что произошло, чем подтверждается, со ссылками на нормы из
справочника. Адвокат правит, а не пишет с нуля. Места, требующие его вмешательства,
подсвечены.

**Затрагивает:** шаг `text` для обоснования во всех визардах, сборку каркаса.

## 2. Регулярное использование

### 2.1. Документ собирается по ходу визарда

**Что не так.** Пока не пройдёшь весь путь, не видно, что получается. Один раз
терпимо, каждый день — невыносимо.

**Как надо.** Документ слева пополняется по мере ответов: выбраны материалы — они
появились в просительной части; выбрана причина — появился абзац мотивировки. Визард
можно оборвать в любой момент и дописать руками — то, что собрано, остаётся.

Это главная правка списка: она лечит и первое знакомство (видно результат), и
ежедневную работу (нет режима «вслепую до конца»).

**Затрагивает:** движок визарда — после каждого шага пересобирать блоки документа;
предпросмотр перестаёт быть единственным местом, где виден результат.

### 2.2. Несколько однотипных позиций в одном визарде

**Что не так.** Вызов трёх свидетелей — это три прохода визарда.

**Как надо.** На шаге данных — «Добавить ещё одного свидетеля»: позиции копятся
списком, документ собирается один, с перечислением. То же для эксперта, для
истребуемых документов, для следственных действий.

**Затрагивает:** визарды `witness`, `expertWitness`, `request`, `action`.

### 2.3. Возврат на шаг и черновик

**Что не так.** Ошибка на втором шаге из четырёх — путь начинается заново.
Прерывание — потеря всего введённого.

**Как надо.** Шаги пронумерованы («шаг 2 из 4»), по клику на номер — возврат с
сохранением ответов. Состояние визарда живёт в карточке дела: если адвокат ушёл в
другой блок и вернулся, черновик на месте.

**Затрагивает:** движок визарда, состояние `state.motionDraft`.

### 2.4. Клавиатура

**Что не так.** Каждый выбор — прицелиться мышью.

**Как надо.** Варианты пронумерованы, нажатие цифры выбирает; Enter подтверждает шаг;
Esc выходит из визарда с сохранением черновика.

**Затрагивает:** обработчик клавиш при активном визарде.

### 2.5. Память о введённых данных

**Что не так.** ФИО свидетеля, экспертное учреждение, адрес вводятся заново каждый
раз, хотя по этому делу уже вводились.

**Как надо.** Всё, что вводится в визарде, сохраняется в карточку дела: свидетели —
в список свидетелей, эксперты и учреждения — в справочник по делу. При следующем
ходатайстве предлагаются первыми.

**Затрагивает:** карточку дела (новые коллекции), шаги `form`.

### 2.6. История ходатайств по делу

**Что не так.** Инструмент не помнит, что такое ходатайство уже подавалось и по нему
получен отказ.

**Как надо.** По каждому делу — список поданных ходатайств: тип, дата, результат.
При запуске визарда того же типа — предупреждение и предложение сослаться на прежний
отказ либо указать новые доводы. Повторное ходатайство без новых доводов бессмысленно,
и об этом лучше сказать до, а не после.

**Затрагивает:** карточку дела, запуск визарда.

### 2.7. Контроль срока рассмотрения

**Что не так.** Срок по ст. 121 УПК РФ упомянут в памятке — этого мало.

**Как надо.** После вставки ходатайства в документ — отметка в деле: подано такого-то
числа, срок рассмотрения истекает такого-то. Памятка остаётся, но появляется факт,
на который можно опереться при обжаловании бездействия.

**Затрагивает:** карточку дела, финал визарда.

## 3. Что остаётся из исходного проекта без изменений

Правки выше не отменяют принятых решений. Сохраняются: три стадии и определение
стадии из карточки; шесть архетипов визарда; двухуровневые списки; сборка обоснования
по схеме «шаблон плюс ИИ-черновик плюс обязательная правка»; все правовые
предохранители, перечисленные в § 9 проекта; экран предпросмотра с чеклистом
готовности — он остаётся, но перестаёт быть единственным местом, где виден документ.

## 4. Порядок реализации

| № | Правка | Почему в этом порядке |
|---|---|---|
| 1 | Живая сборка документа по ходу визарда (§ 2.1) | Меняет архитектуру движка; делать после — переписывать |
| 2 | Возврат на шаг и черновик (§ 2.3) | Тоже архитектура визарда, делается вместе с первым |
| 3 | Объединение недопустимости и исключения (§ 1.1) | Правка каталога и одного определения, дешёвая |
| 4 | Названия стадий (§ 1.2) | Правка строк |
| 5 | Пресеты и объяснение недоступных пунктов (§ 1.3, 1.4) | Рендер списков |
| 6 | Обоснование с заготовкой (§ 1.5) | Требует готовых каркасов по типам |
| 7 | Несколько позиций в одном визарде (§ 2.2) | Затрагивает четыре визарда |
| 8 | Клавиатура (§ 2.4) | Поверх готового движка |
| 9 | Память о данных (§ 2.5) | Требует расширения карточки дела |
| 10 | История ходатайств и срок (§ 2.6, 2.7) | Требует новой сущности в карточке |

Пункты 1–6 меняют то, вернётся ли адвокат в инструмент завтра. Пункты 7–10 — про
удобство ежедневной работы; их можно вводить постепенно.
